# Implementation evidence — 2026-10-22

- **Documented:** C2PA stores PNG manifest data in `caBX`, as defined by the [C2PA PNG embedding specification](https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html#_embedding_manifests_into_png). The shared registry recognizes the chunk without claiming that its mere presence is valid C2PA. PNG CRCs remain a separate structural check.
- **Documented and observed:** [c2patool v0.28.2](https://github.com/contentauth/c2patool/tree/v0.28.2) ordinary JSON output contains a manifest store and independent top-level `validation_results`. The `--info` branch returns before `configure_sdk` in [main.rs](https://github.com/contentauth/c2patool/blob/v0.28.2/src/main.rs); it is unsuitable for the intended offline validation call. The integration supplies an explicit settings path and reads ordinary JSON.
- **Documented:** The [SDK settings](https://github.com/contentauth/c2pa-rs/blob/main/sdk/src/settings/mod.rs) define an empty `core.allowed_network_hosts` list as blocking traffic. Identity assertion decoding is disabled because the settings documentation notes a host-allowlist exception for that subsystem. Remote manifest fetching and OCSP fetching are explicitly disabled. Pinned runtime/settings fingerprints make these implementation assumptions version-specific.
- **Observed:** The supplied Gemini PNG produces two manifests, one `parentOf` ingredient edge and 344 native PNG blocks. Grouping consecutive IDAT produces four display groups. Independent top-level validation reports active claim signature and data-hash matches and trust against the bundled snapshot. Earlier success records are nested inside an ingredient and are treated as embedded historical claims; the validator's independent ingredient deltas remain separate.
- **Observed:** The official `sample/C.jpg` validates its claim signature and file hash while reporting `signingCredential.untrusted` against the bundled trust list. Changing an entropy-data byte preserves the claim signature but makes the content binding fail. These are distinct tested properties in the application.
- **Documented and observed:** [ExifTool's JSON group options](https://exiftool.org/exiftool_pod.html#j-JSON) preserve duplicate instances with family 4 grouping. `RequestAll=3` also requests scanner-generated values. Namespace-based classification marks the entire `ExifTool` family as diagnostics, `Composite` as derived values and `File:System` as filesystem data; volatile diagnostics are excluded from comparison.
- **Documented:** [ComfyUI SaveImage](https://github.com/Comfy-Org/ComfyUI/blob/master/nodes.py) embeds prompt/workflow JSON, and [AUTOMATIC1111 infotext](https://github.com/AUTOMATIC1111/stable-diffusion-webui/blob/master/modules/infotext_utils.py) supplies generation parameters. These recognizers remain independent from C2PA actions. No additional parameter convention is claimed.

Remaining inference limits are recorded in README and in each result. No model, account, seed, prompt, physical creator identity or watermark presence is inferred from application names or signature trust.

## Camera/capture summary — 0.4.0

- **Documented:** The [ExifTool EXIF tag table](https://exiftool.org/TagNames/EXIF.html) maps `Make`/`Model` to device identity claims, `DateTimeOriginal` to original capture time, `OffsetTimeOriginal` to its timezone offset, `SubSecTimeOriginal` to its fractional seconds, and `SerialNumber` to EXIF BodySerialNumber. Lens identifiers, exposure, f-number, ISO, focal length, flash and GPS values have separate tags. Filesystem time is never a fallback capture time.
- **Documented:** The [XMP tag table](https://exiftool.org/TagNames/XMP.html) defines relevant `tiff`, `exif`, `exifEX` and `aux` camera namespaces. The [QuickTime table](https://exiftool.org/TagNames/QuickTime.html#Keys) defines make/model keys, including `AndroidMake` and `AndroidModel`. Model-like names in other namespaces have different meanings and are not generic device evidence.
- **Observed in the pinned ExifTool 13.59 source and a real Canon sample:** camera `Model` belongs to EXIF IFD0; model fields in thumbnail IFD1 must not override it. Root asset fields are grouped as `Main`, while embedded subdocuments use `Doc` indices. Duplicate fields remain separately grouped. MakerNote exposure values can differ in representation from standard EXIF values (Canon's reported exposure of 128 versus standard EXIF 4 seconds in the local sample); only MakerNote identity/lens tags feed this summary, with exposure taken from standard EXIF/XMP.
- **Implementation:** retain all source fields and numeric counterparts for each summary property, merge only case/outer-whitespace-equivalent displayed values, and flag multiple distinct identity values as a disagreement without treating that as proof of tampering. No device database, visual classifier, online lookup, timezone inference or identity authentication is added.
